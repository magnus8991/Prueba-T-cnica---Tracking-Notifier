# ADR-001: Notificación confiable con Transactional Outbox en PostgreSQL

- **Estado:** Aceptada
- **Fecha:** 2026-11-18
- **Contexto de negocio:** los clientes quieren enterarse "casi en tiempo real, sin perder eventos"; el envío no debe bloquear la respuesta; hasta 5 intentos con espera creciente.

## Contexto

Por cada evento aceptado hay que:

1. guardar el evento y actualizar la guía, y
2. hacer un `POST` al webhook del tenant, de forma asíncrona y con reintentos.

Son dos sistemas distintos (nuestra BD y el sistema del cliente) y no existe una transacción que abarque ambos. Si se resolviera de forma ingenua aparecen ventanas de pérdida:

| Alternativa | Problema |
|---|---|
| Enviar el webhook dentro del request | Bloquea la respuesta (lo prohíbe el RF4); un cliente lento degrada la API |
| Guardar y luego `setImmediate`/cola en memoria | Si el proceso cae entre el `COMMIT` y el envío, **la notificación se pierde**; los reintentos programados en memoria también se pierden |
| Guardar y publicar en un broker (Pub/Sub, Kafka) | *Dual write*: el commit puede funcionar y la publicación fallar (o al revés). Además agrega infraestructura que la prueba no exige |

## Decisión

Usar el patrón **Transactional Outbox** sobre la misma base PostgreSQL:

1. En **una sola transacción** se insertan el evento (`tracking_events`), el estado de la guía (`shipments`) y una fila `notifications` en estado `PENDIENTE`. O se guardan las tres cosas o ninguna.
2. Un **despachador** (worker en el mismo proceso, desactivable con `APP_ROLE`) reclama trabajo con:
   ```sql
   SELECT id FROM notifications
    WHERE (status='PENDIENTE' AND next_attempt_at <= now())
       OR (status='ENVIANDO' AND locked_until < now() AND attempts < max_attempts)
    ORDER BY next_attempt_at LIMIT :n
    FOR UPDATE SKIP LOCKED
   ```
   Marca las filas `ENVIANDO`, cuenta el intento y toma un *lease* (`locked_until`).
3. Envía el webhook fuera de la transacción (timeout de 5 s) y guarda el resultado:
   - 2xx: `ENVIADA`.
   - Fallo con intentos disponibles: `PENDIENTE` con `next_attempt_at = now + backoff(n)`.
   - Fallo en el 5.º intento: `FALLIDA`, que queda consultable y se puede reintentar manualmente.
4. Tras el commit, la API "despierta" al worker en memoria para no esperar al siguiente ciclo de polling. Si esa señal se pierde, el polling (1 s) recoge el trabajo igual: la señal es una optimización, no un requisito de corrección.

Idempotencia: `PRIMARY KEY (tenant_id, event_id)` en eventos y `UNIQUE (tenant_id, event_id)` en notificaciones. Las peticiones concurrentes con el mismo `eventId` se serializan con `pg_advisory_xact_lock`, y la BD sigue siendo la última defensa.

## Consecuencias

**Positivas**

- **Sin pérdida de eventos:** la notificación existe si y solo si el evento existe (atomicidad de PostgreSQL).
- **Resiliencia ante caídas:** si un worker muere mientras envía, el *lease* vence y otro worker retoma la notificación. Si la caída ocurre en el último intento, no se hace un 6.º envío: la notificación queda `FALLIDA` (`LEASE_EXPIRADO`).
- **Escala horizontal:** `SKIP LOCKED` permite N réplicas compitiendo por la cola sin bloquearse ni duplicar trabajo. Está verificado con una prueba de integración.
- **Reintentos durables:** el *backoff* vive en `next_attempt_at`, no en memoria, así que sobrevive a reinicios y despliegues.
- **Sin infraestructura extra:** solo PostgreSQL, que ya exige el enunciado. Es simple de operar y de explicar.
- **Auditable:** `notification_attempts` guarda cada intento (status HTTP, error, duración).

**Negativas / riesgos aceptados**

- **Entrega *at-least-once*:** si el cliente recibe el POST pero el resultado no se alcanza a guardar, se reenviará. Mitigación: la cabecera `webhook-id` (= `eventId`) es estable entre reintentos para que el cliente deduplique, como recomienda Standard Webhooks.
- **Carga de polling sobre la BD:** se acota con el índice parcial `WHERE status IN ('PENDIENTE','ENVIANDO')`, lotes y un intervalo configurable. Si el volumen crece se puede migrar a `LISTEN/NOTIFY` o a un relay hacia Pub/Sub.
- **No hay orden garantizado entre notificaciones de una misma guía** durante los reintentos. El payload trae `fechaEvento` y el historial (RF2) es la fuente de verdad del orden.
- **En Cloud Run** el worker en segundo plano necesita CPU siempre asignada. Se resuelve con `APP_ROLE=worker` en un servicio aparte con `--no-cpu-throttling` y `min-instances=1` (ver `docs/despliegue-gcp.md`).

## Alternativas consideradas para el futuro

- **Outbox → Google Cloud Pub/Sub (relay/CDC con Datastream o Debezium)** cuando haya varios consumidores del evento o volúmenes altos.
- **Cloud Tasks por notificación:** delega reintentos y *rate limiting* a GCP, pero con el riesgo de *dual write* salvo que se combine con el outbox.
